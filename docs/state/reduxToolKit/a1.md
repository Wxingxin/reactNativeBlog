# 一、createAsyncThunk 是什么（一句话版）

> **createAsyncThunk = Redux 官方推荐的“异步 action 工厂”**
> 用来：

* 发请求
* 自动生成 `pending / fulfilled / rejected`
* 把异步流程纳入 Redux 状态机管理

它解决的是：**“请求状态怎么统一、可预测、可复用”**。

---

# 二、最标准的 createAsyncThunk 写法（你给的例子，完整版）

```js
// features/user/userThunks.js
import { createAsyncThunk } from "@reduxjs/toolkit";
import api from "../../api";

export const fetchUser = createAsyncThunk(
  "user/fetch",               // action type 前缀
  async (id, thunkAPI) => {
    const res = await api.get(`/user/${id}`);
    return res.data;           // 👉 进入 fulfilled 的 payload
  }
);
```

### action type 实际会变成 3 个

```txt
user/fetch/pending
user/fetch/fulfilled
user/fetch/rejected
```

**这是面试必说点**。

# 三、loading / error 状态设计（必须掌握）

## 1️⃣ 最推荐的 state 结构（可扩展、可并发）

```js
const initialState = {
  data: null,
  status: "idle",   // idle | loading | succeeded | failed
  error: null,
};
```

### 为什么不用 boolean？

❌ `isLoading: true/false`
✅ `status: 'loading'`

原因：

* 可表达更多状态
* 日志 / 调试 / 并发更清晰
* 面试官非常认可

---

## 2️⃣ 在 slice 中处理 pending / fulfilled / rejected

```js
// features/user/userSlice.js
import { createSlice } from "@reduxjs/toolkit";
import { fetchUser } from "./userThunks";

const userSlice = createSlice({
  name: "user",
  initialState,
  reducers: {},
  extraReducers: (builder) => {
    builder
      .addCase(fetchUser.pending, (state) => {
        state.status = "loading";
        state.error = null;
      })
      .addCase(fetchUser.fulfilled, (state, action) => {
        state.status = "succeeded";
        state.data = action.payload;
      })
      .addCase(fetchUser.rejected, (state, action) => {
        state.status = "failed";
        state.error = action.error.message;
      });
  },
});

export default userSlice.reducer;
```

# 四、页面 loading / 成功 / 失败：完整使用模式

```jsx
const UserPage = ({ userId }) => {
  const dispatch = useDispatch();
  const { data, status, error } = useSelector((s) => s.user);

  useEffect(() => {
    dispatch(fetchUser(userId));
  }, [userId, dispatch]);

  if (status === "loading") return <Loading />;
  if (status === "failed") return <Error message={error} />;
  if (!data) return null;

  return <UserCard user={data} />;
};
```

👉 **这是你项目里 80% 页面都会用的范式**

# 五、防止重复请求（并发控制）✅ 面试高频

## 方式一：在组件层“状态判断”（最常用）

```js
useEffect(() => {
  if (status === "idle") {
    dispatch(fetchUser(userId));
  }
}, [status, userId]);
```

**优点**

* 简单
* 可读性强

---

## 方式二：createAsyncThunk 的 `condition`（更专业）

```js
export const fetchUser = createAsyncThunk(
  "user/fetch",
  async (id) => {
    const res = await api.get(`/user/${id}`);
    return res.data;
  },
  {
    condition: (id, { getState }) => {
      const { user } = getState();
      if (user.status === "loading") {
        return false; // ❗取消本次 thunk
      }
    },
  }
);
```

**面试官听到这一句会加分**：

> “我们会在 thunk 的 condition 中阻止重复请求。”

# 六、thunk 参数与返回值（一定要讲清楚）

## thunk 接收什么？

```js
async (arg, thunkAPI) => {}
```

### arg

```js
dispatch(fetchUser(123));
// arg === 123
```

### thunkAPI 常用内容

```js
{
  dispatch,
  getState,
  rejectWithValue,
  signal,
}
```

---

## 返回值流向（非常重要）

```js
return res.data;
// ↓
fulfilled(action.payload === res.data)
```

```js
throw error;
// ↓
rejected(action.error)
```

### 推荐：用 `rejectWithValue`

```js
return rejectWithValue("用户不存在");
```

```js
.addCase(fetchUser.rejected, (state, action) => {
  state.error = action.payload; // 自定义错误
});
```

# 七、📌 面试必问点（重点背）

---

## Q1：thunk 和 useEffect 的边界？

### 标准答案（直接用）

> **useEffect 负责“什么时候发请求”**
> **thunk 负责“请求怎么发、状态怎么流转”**

| 层级        | 职责                 |
| --------- | ------------------ |
| useEffect | 生命周期 / 依赖变化        |
| thunk     | 异步逻辑、dispatch、错误处理 |
| reducer   | 状态变化               |

❌ 错误做法：在 useEffect 里直接写请求 + setState
✅ 正确：useEffect 只 dispatch thunk

---

## Q2：thunk 能否访问 state？

### 正确答案

> **可以，通过 `getState()`**

```js
async (arg, { getState }) => {
  const token = getState().auth.accessToken;
  return api.get("/user", {
    headers: { Authorization: token },
  });
}
```

### 常见用途

* 取 token
* 判断是否已加载
* 防止重复请求
* 多 slice 协同

---

## Q3：并发请求怎么处理？

你可以回答：

1. 状态机（status）
2. condition 阻断
3. requestId（RTK 内部已支持）
4. abort（signal）

**一句话总结**：

> “RTK 的 thunk 天生支持并发可控的异步流程。”
