## 1) 整体数据流（最重要的一张脑图）

以页面加载后触发 `dispatch(fetchUser(1))` 为例：

1. React 组件（`App.jsx`）触发 `dispatch(fetchUser(userId))`
2. `fetchUser` 是 `createAsyncThunk` 生成的 thunk action creator
3. thunk 运行后，RTK 自动派发：

   * `user/fetch/pending`
4. `userSlice.extraReducers` 监听到 `pending`：

   * 把 `state.user.status` 改成 `"loading"`，清空 `error`
5. React 里 `useSelector(selectUserStatus)` 订阅到 status 变化：

   * `App` 重新渲染，显示 `<Loading />`
6. thunk 内部真正执行 async：

   * 调 `api.get('/users/1')` 发请求
7. 请求成功：RTK 自动派发

   * `user/fetch/fulfilled`，并带上 `payload = res.data`
8. `extraReducers` 处理 `fulfilled`：

   * `status = "succeeded"`
   * `data = action.payload`
9. `useSelector(selectUserData)` 发现 data 变化：

   * `App` 重新渲染，显示用户卡片
10. 如果请求失败：自动派发

    * `user/fetch/rejected`，带 `action.error`
    * `status = "failed"`，`error = action.error.message`
    * `App` 渲染 `<ErrorView />`

这条链路就是 Redux 异步“状态机”的核心。

## 2) Provider + store：为什么组件里能用 useDispatch/useSelector？

### `src/main.jsx`

```jsx
<Provider store={store}>
  <App />
</Provider>
```

**作用**

* `Provider` 把 `store` 放进 React Context
* 之后所有子组件都能通过：

  * `useDispatch()` 拿到 `store.dispatch`
  * `useSelector()` 订阅 `store.getState()`

没有 Provider，hooks 会报错，因为找不到 store。

## 3) store 里 reducer 的 key 决定 state 的形状

### `src/app/store.js`

```js
export const store = configureStore({
  reducer: {
    user: userReducer,
  },
});
```

**结论**

* 全局 state 结构固定为：

```js
state = {
  user: {
    data: null,
    status: "idle",
    error: null,
  }
}
```

你在组件里写的 `state.user.status` 就是从这里来的。

## 5) createAsyncThunk：参数怎么传？返回值去哪了？

### 5.1 你 dispatch 的是什么？

在 `App.jsx`：

```js
dispatch(fetchUser(userId));
```

* `fetchUser` 是 thunk action creator
* `fetchUser(userId)` 的 `userId` 就是 thunk 的 **arg**

### 5.2 thunk 定义里怎么接收？

在 `userThunks.js`：

```js
async (id, thunkAPI) => {
  const res = await api.get(`/users/${id}`);
  return res.data;
}
```

* `id` 就是刚才 `userId`
* `return res.data` 会成为 `fulfilled` 的 `action.payload`

### 5.3 fulfilled 的 action 形态大概长这样

```js
{
  type: "user/fetch/fulfilled",
  payload: { id: 1, name: "...", email: "..." },
  meta: { arg: 1, requestId: "xxx", ... }
}
```

## 6) pending/fulfilled/rejected 是谁派发的？你派发了吗？

你没有手动 dispatch pending/fulfilled/rejected。

RTK 在 thunk 生命周期中自动 dispatch：

* thunk 开始：dispatch `pending`
* thunk resolve：dispatch `fulfilled`
* thunk reject：dispatch `rejected`

所以你只需要写：

* thunk 的 async 函数（如何请求）
* slice 的 extraReducers（如何变更状态）

## 7) extraReducers：为何不写在 reducers 里？

在 `userSlice.js`：

```js
extraReducers: (builder) => {
  builder
    .addCase(fetchUser.pending, ...)
    .addCase(fetchUser.fulfilled, ...)
    .addCase(fetchUser.rejected, ...);
}
```

**原因**

* `reducers` 主要处理本 slice 自己的同步 action（如 `clearUser`）
* `extraReducers` 用来处理“外部 action”

  * thunk 自动生成的 action 就属于外部 action（pending/fulfilled/rejected）

## 8) 为什么 reducer 里可以 “直接改 state”？

在 `pending`：

```js
state.status = "loading";
state.error = null;
```

**本质**

* 这里的 `state` 是 immer 的 draft（代理对象）
* 你改 draft，immer 帮你生成新的不可变 state
* Redux 最终接收到的是新对象，所以仍然满足不可变更新

## 9) 页面渲染为何会自动变化？useSelector 的订阅机制

在 `App.jsx`：

```js
const status = useSelector(selectUserStatus);
```

selector：

```js
export const selectUserStatus = (state) => state.user.status;
```

**发生了什么**

* `useSelector` 会订阅 store
* 当 `state.user.status` 改变时，React 触发组件重新渲染
* 所以你写的：

```jsx
{status === "loading" && <Loading />}
```

会自动在状态变化时切换 UI

## 10) 防止重复请求：condition 具体怎么阻止并发？

在 `createAsyncThunk` 第三个参数：

```js
{
  condition: (id, { getState }) => {
    if (getState().user.status === "loading") return false;
  }
}
```

**效果**

* 当你疯狂点 “Fetch (manual)” 时
* 如果当前已经 `loading`
* 新的 thunk **不会执行**
* 也不会触发 `pending`（因此 UI 不会乱跳）

这是“最便宜、最常用”的并发控制方式。

> 注意：它阻止的是“同一时刻重复发起”。
> 它不是取消正在进行的请求。取消要用 `signal/AbortController`。

## 11) thunk 和 useEffect 的边界（你这套代码怎么体现）

### useEffect 做什么？

```js
useEffect(() => {
  dispatch(fetchUser(userId));
}, [userId, dispatch]);
```

**职责**：决定“什么时候触发请求”

* 页面首次渲染
* userId 改变

### thunk 做什么？

```js
async (id) => api.get(...)
```

**职责**：决定“请求怎么发、状态怎么流转”

* pending/fulfilled/rejected
* 数据进入 store
* 错误进入 store

这就是标准的边界划分。
